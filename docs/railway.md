# Deploy on Railway

Use a **new, dedicated Railway project** for this configuration. Project-level IaC can remove resources that are not declared in the file; do not apply it to a project with unrelated services. Railway usage and database storage are billed to your account.

The root `Dockerfile` builds React and Go into one unprivileged application container. `.railway/railway.ts` provisions that container, PostgreSQL with persistent storage, and Redis, and connects them using Railway variable references. Database passwords are generated by Railway, not stored in this repository. `compose.yaml` remains the local-development setup; Railway does not deploy its services automatically when you connect a GitHub repository.

## First deployment

Merge the deployment PR into `main` first: the configuration tracks `theashgen/quiz` on `main`. Install Node.js 24 or newer and Railway CLI **5.42.1 or newer**, and authorize Railway's GitHub integration to access the repository.

From the repository root:

```sh
npm install -g @railway/cli
npm ci --prefix .railway
railway login
railway init
railway config plan
railway config apply
railway domain --service quiz
railway redeploy --service quiz
```

Choose a new project named `quiz` during `railway init`. Review the plan: it should create only `quiz`, `postgres`, and `redis` and their database storage. `apply` provisions those services and their environment references. Generate the public domain for `quiz`, then redeploy so the app receives `RAILWAY_PUBLIC_DOMAIN`. Initial app attempts may fail until the database and public domain are ready; failed starts are retried up to ten times.

If you already created an **empty** project in the dashboard, use `railway link` instead of `railway init`.

After this one-time setup, pushes to `main` deploy the GitHub-connected app using the root Dockerfile. Infrastructure edits require another reviewed `railway config plan` and `railway config apply`; merely pushing the IaC file does not provision resources.

## Runtime and database commands

| Service | Build or startup | Configuration |
| --- | --- | --- |
| `quiz` | Dockerfile builds the UI and Go binary; `/app/quiz` starts the server | `DATABASE_URL` and `REDIS_URL` reference the database services |
| `postgres` | Railway PostgreSQL service starts PostgreSQL | Railway provisions credentials and persistent database storage |
| `redis` | Railway Redis service starts Redis | Railway provisions its connection URL |

Go applies `migrations/*.sql` automatically at startup under a PostgreSQL advisory lock and transaction, before serving requests. Do not add a separate SQL initialization or seed command. Deploy one app replica initially; validate multi-replica room behavior before scaling.

Railway terminates public HTTPS and forwards HTTP to Go. `BEHIND_PROXY=true` enables that listener on `[::]:$PORT` (or port 8443 if `PORT` is unset), while retaining secure `__Host-` cookies. **Do not set `LOCAL_HTTP=true` in Railway**, and do not expose the plain-HTTP listener outside the trusted proxy network. No TLS certificate files or local certificate mounts are needed. The image includes CA certificates for TLS connections to external services.

The allowed browser origin defaults to `https://$RAILWAY_PUBLIC_DOMAIN`. For a custom domain, set `APP_ORIGIN` on `quiz` to the exact HTTPS origin, without a trailing slash. Multiple allowed origins are comma-separated. Update and redeploy the app when changing domains. Host the UI and backend together so secure session cookies and WebSockets remain same-origin.

`/api/health` returns HTTP 200 only when PostgreSQL is reachable; its JSON also reports Redis connectivity. Railway uses this endpoint to check a deployment before routing traffic to it.

## Verify and troubleshoot

```sh
railway logs --service quiz
npm test --prefix .railway
go test ./cmd/server ./internal/sessions
```

Open the generated HTTPS domain and verify teacher signup, room creation, joining, and a live round. No production Railway deployment has been verified by the repository's local tests.

- `database startup`: verify PostgreSQL is running and `DATABASE_URL` references the `postgres` service. A newly created database may still be starting; redeploy once ready.
- `BEHIND_PROXY requires APP_ORIGIN or RAILWAY_PUBLIC_DOMAIN`: generate the app's public domain and redeploy, or explicitly set `APP_ORIGIN`.
- Browser actions fail origin checks: match `APP_ORIGIN` exactly to the URL in the browser, including its scheme and any non-default port.
- Missing SDK import: run `npm ci --prefix .railway` before planning.
- Back up PostgreSQL before applying new migrations; migrations are forward-only and rollback of an app deployment does not undo database changes.
